**가장 중요한 다섯 가지**

0. **공유 세션 DB를 세 번 리셋했다.** `docs/experiments/reset_demo_data.py`가
   `SAIFE_BASE_URL`을 보지 않고 `docker exec saife-postgres`를 직접 때리는 걸
   모르고, 격리된 `saife-clean` 스택에 스모크를 돌리며 그대로 실행했다.
   `saife-postgres`(5433, 동시에 읽기 전용 리뷰어의 비전 테스트가 쓰던 컨테이너)의
   `work_plan`/`incident`/`hazard.ai_adopted` 등이 시드 경계로 리셋됐다. 되돌릴 수
   없다. 스크립트에 `SAIFE_PG_CONTAINER` 환경변수를 추가해 재발을 막았다(아래 상세).
1. **컨테이너 스택에서 법정 서식 버튼이 전부 404였다.** `frontend/nginx.conf`에
   `/api/`만 있고 `/form/`이 없었다 — 개발 중엔 Vite 프록시가 가려서 안 보였다.
2. **Windows 클론이면 백엔드 도커 이미지가 아예 안 빌드됐다.** `backend/gradlew`가

3. **스모크 스크립트 자체에 두 개의 오탐(false positive/negative)이 있었다.**

   `today_smoke.py`는 자기가 방금 만든 작업계획서가 아니라 날짜가 먼 다른 계획서를
   집어서 엉뚱한 걸 승인했다. 둘 다 실제 앱 동작은 정상이었다 — 스모크의 판정
   로직 버그였다.
4. **근거 계층은 헬시 이후에도 비동기로 계속 적재된다.** `GET /actuator/health`가
   UP을 찍어도 근거 청크 41,281건이 전부 들어오기까지 약 2분이 더 걸린다.
   그 사이에 근거 카드가 얇게 나올 수 있다 — README·deployment.md에 명시했다.

## C. 이번 라운드(Task 6a)가 새로 찾은 것

### C1 — nginx `/form/` 프록시 없음 (Critical)

컨테이너 스택에서 `/form/work-plan/{id}` 등 법정 서식 페이지가 전부 404였다.
`frontend/nginx.conf`는 `/api/`만 `backend:8080`으로 넘기고 `/form/`은 비어 있었다 —
개발 중엔 Vite 프록시가 `/form`도 넘겨서 이 문제가 한 번도 드러나지 않았다.
`/api/`와 같은 대상으로 `/form/` 블록을 추가하되, SSE 버퍼링 옵션은 `/api/` 전용으로
남겼다(서식 페이지는 스트림이 아니다). **실측**: 수정 전 `curl -o /dev/null -w '%{http_code}'
http://localhost:5174/form/work-plan/1` → 404, 수정 후 → 200.

수정: `4a10440`.

### C2 — `backend/gradlew` CRLF 체크아웃이 도커 빌드를 깬다 (Critical)

Windows(`core.autocrlf=true`)에서 clone하면 `backend/gradlew`가 CRLF로 체크아웃된다.
git object 자체는 LF인데(`git show HEAD:backend/gradlew`로 확인) 체크아웃 필터가
없어 워킹트리에서 CRLF로 풀린다. 컨테이너 안에서 셔뱅(`#!/bin/sh\r`)이 깨져
`./gradlew: not found`(exit 127)로 백엔드 이미지 빌드가 통째로 실패한다.
`.gitattributes`로 `gradlew`는 항상 LF, `*.bat`은 항상 CRLF로 고정했다.

**영향 범위**: 심사위원이 Windows에서 `git clone` + `docker compose up -d --build`를
그대로 따라했다면 100% 재현됐을 것이다 — `deployment.md` 5분 룰이 macOS/Linux
개발 환경에서만 검증돼 있었다.

수정: `abc2f63`.

### C3 — `today_smoke.py`: 승인 대상 작업계획서를 잘못 고른다 (Medium, 테스트 버그)

`GET /api/work-plan?page=0&size=1`(`ORDER BY work_date DESC`)의 첫 행을 "방금 만든
계획서"로 가정했는데, 다른(이전 스모크 실행이 남긴) 작업계획서가 더 먼 미래 날짜로
이미 SUBMITTED 상태면 그게 먼저 온다. 실측: "내일" 날짜로 등록한 계획서(id=14) 대신
11월 날짜의 다른 계획서(id=11)를 골라 승인해버려 RISKY_WORK_PLAN 확인이 실패했다.
`createWorkPlan`의 응답 문구("작업계획서 제출 완료 [id=N]")에서 직접 id를 추출하도록
고쳤다 — 앞쪽 턴에 반복되는 "설비 확인됨 [id=N]"(설비 id, 다른 의미)과 구분하기 위해
"완료 [id=N]" 접미사로 좁혔다. **제품 코드 버그가 아니다** — 작업계획서 목록 API
자체는 명세대로(날짜 내림차순) 동작한다.

수정: `b058963`(docs/experiments/today_smoke.py).

### C4 — `baseline_connectivity.py`: 성공한 호출도 "연결 실패"로 오판 (Low, 테스트 버그)

`b2_status` 판정이 `"error" in per_call_dict`로 되어 있었는데, 성공한 호출의
딕셔너리에도 `"error"` 키가 항상 존재한다(값이 `None`일 뿐). 그래서 10회 전부
HTTP 200으로 성공해도 매번 `CONNECTION_FAILED`("측정 불가")로 잘못 찍혔다.
요청 자체가 실패했을 때만 서는 `request_failed` 플래그로 분리했다. 고친 뒤
재실행하면 `b2_status=OK`로 정확히 뜬다(아래 §M2 참고 — 그래도 회상 텍스트/이벤트는
0/10인데, 이건 별개의 **알려진·불변의** 원인이다: 이 스크립트가 쓰는 고정 문구는
같은 위치에 설비가 2건이라 위치 텍스트만으로는 의도적으로 모호하다).

수정: `b058963`(docs/experiments/baseline_connectivity.py).

### C5 — `reset_demo_data.py`가 컨테이너 이름을 하드코딩 → 공유 DB 오조작 (사고 기록)

`docs/experiments/reset_demo_data.py`는 `SAIFE_BASE_URL`을 전혀 보지 않고
`docker exec saife-postgres psql ...`로 **컨테이너 이름을 직접** 지정한다.
Task 6a는 격리된 `saife-clean-postgres`(5434)에 스모크를 돌리는 게 원칙이었는데,
"`SAIFE_BASE_URL`만 클린 스택으로 바꾸면 리셋도 거기로 간다"고 착각하고 이 스크립트를
세 차례 그대로 실행했다. 실제로는 매번 **공유 세션 DB**(`saife-postgres`, 5433 —
이 세션과 동시에 읽기 전용 리뷰어의 비전 테스트가 쓰고 있던 컨테이너)를 시드 경계로
되돌렸다(`work_plan`/`incident`를 id=1만 남기고 삭제, `hazard.ai_adopted` 복원,
`conversation`/`tool_call` 전부 삭제).

**되돌릴 수 없다.** 영향 범위를 확인한 결과 리셋 시점에 활성 DB 연결은 없었고(
`pg_stat_activity` 확인), 리셋 후 상태는 "깨진" 상태가 아니라 정상적인 시드 경계
상태다 — 그러나 리뷰어가 리셋 이전에 뭔가 쌓아두고 있었다면 그 데이터는 사라졌다.
**컨트롤러/사용자가 동시 실행 중이던 비전 테스트 세션에 이 사실을 확인해야 한다.**

재발 방지: `SAIFE_PG_CONTAINER` 환경변수를 추가해 대상 컨테이너를 명시하게 했고,
스크립트 docstring과 `README.md`·`.claude/rules/deployment.md`에 굵게 경고를 남겼다.

수정: `b058963`(docs/experiments/reset_demo_data.py) + 문서.

### C6 — `TodayServiceTest`가 오염된 공유 DB에서 실패할 수 있음 (정보성)

`./gradlew cleanTest test`를 `saife-clean-postgres`(이미 내 스모크 대화들이 만든
assessment/work_plan 잔여물이 있는 상태)에 대고 돌렸더니 255건 중 1건
(`periodicDue_within60Days_included`)이 실패했다. 테스트는 "가장 최근 평가"를
찾는데, DB에 테스트가 기대한 것보다 더 최근 날짜(오늘 실행된 스모크 대화가 만든
평가)가 이미 있어서 다른 행을 골랐다 — **코드 결함이 아니라 테스트 격리 부재**다
(F-IT1 계열과 같은 범주: 빈 DB를 가정한 절대 비교가 채워진 DB에서 깨진다).
비어 있는 DB(또는 Testcontainers)에서 재확인이 필요하다. Testcontainers 전환은
스펙 §12에서 이미 범위 밖으로 명시돼 있다.
