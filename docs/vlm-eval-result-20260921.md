# VLM 평가셋 — 게이트 재확인

- **실행**: 2026-09-21 (게이트와 같은 날, 게이트 직후)
- **모델**: `gemini-3.8-flash`, 라이브 호출 (`demoMode: false` 전건 확인)
- **기준**: [`vlm-gate-rules-20260921.md`](vlm-gate-rules-20260921.md) — **게이트와 동일한 규칙을 그대로 적용**
- **판독 대상**: 평가셋 22장 (게이트 30장과 **겹침 0**)
- **기록**: `docs/experiments/eval_findings.json` · `eval_adjudication.json`

평가셋은 게이트의 결론을 **다시 시험하기 위한 것**이지 새 주장을 만들기 위한 것이 아니다.
그래서 기준을 바꾸지 않았고, 판독 코드도 게이트와 같은 함수를 지난다
(`vlm_gate.py`의 `run()`에 세트 경로만 바꿔 넣는다).

## 결정

> ## 재현됨 — 통과 3축이 게이트와 **완전히 일치**한다
>
> `FALL` · `DROP` · `PPE` 통과 / `CAUGHT` · `STRUCK` · `FIRE` 미통과.
> 게이트 결과를 수정할 이유가 없다. `GateStatus` 표를 그대로 둔다.

| 축 | 게이트 (30장) | 평가셋 (22장) | 일치 |
|---|---|---|---|
| `FALL` 추락 | 채택 9 / 장수 8 / **통과** | 채택 3 / 장수 3 / **통과** | ✓ |
| `PPE` 보호구 | 채택 8 / 장수 8 / **통과** | 채택 3 / 장수 3 / **통과** | ✓ |
| `DROP` 낙하 | 채택 3 / 장수 3 / **통과** | 채택 3 / 장수 3 / **통과** | ✓ |
| `STRUCK` 부딪힘 | 채택 2 / 장수 2 / 미통과 | 채택 2 / 장수 2 / 미통과 | ✓ |
| `FIRE` 화재 | 채택 2 / 장수 2 / 미통과 | 채택 3 / 장수 2 / 미통과 | ✓ |
| `CAUGHT` 협착 | 채택 1 / 장수 1 / 미통과 | 채택 0 / 장수 0 / 미통과 | ✓ |

전체: 22장 판독, 후보 16건. **채택 14 · 반려 2** (반려율 12.5%).
게이트는 11%였다. 두 세트의 반려율이 거의 같다.

## ⚠️ 축별 n을 반드시 같이 말한다

**평가셋은 30장이 아니라 22장이다.** 원본 부족으로 두 축이 1장밖에 없다.

| 축 | 평가셋 n | 비고 |
|---|---:|---|
| `FALL` `DROP` `STRUCK` `FIRE` | 각 5 | 건설 데이터셋 |
| `CAUGHT` | **1** | 제조 jam 시퀀스가 5개뿐. 게이트가 5개를 다 썼다 |
| `PPE` | **1** | 선박 안전장비 라벨 이미지가 6장뿐 |

→ **`CAUGHT`의 평가셋 미통과는 모델 결과가 아니라 표본 결과다.** 1장에서 후보 0건인 것으로
축을 평가할 수 없다. 게이트(5장)의 판정이 이 축에 대한 유일한 근거다.

→ `PPE`가 평가셋에서 통과한 것은 **다른 세트의 사진에서 나온 `PPE` 후보** 덕분이다
(제조 1 + 화재 2). 축 집계는 세트가 아니라 후보의 `accidentType` 기준이고,
이건 게이트에서 정한 그대로다.

**발표에서 "축당 5장"이라고 말할 수 없다.** 축별 n을 슬라이드에 적는다.

## 게이트에서 남긴 숙제 — 결과

### 1. `DROP`의 마진이 없다 → **두 번 다 정확히 3장**

게이트 3장, 평가셋 3장. 두 번 연속 기준선에 딱 걸렸다.

우연이 아니라 **구조적**으로 보인다. 낙하 세트 5장 중 후보가 나오는 것이
3장 언저리이고, `DROP` 후보의 성격이 두 가지로 갈린다:

- **적재 불량** (2건) — 발판 위 페인트 통, 사다리차 위 판넬 더미. 대상이 프레임 안에 있어 확정 쉽다
- **낙하물 방지망 미설치** (1건) — 비계 외측 전체를 봐야 한다. 프레임에 다 안 잡히면 못 낸다

**`DROP`은 통과했지만 "여유 있게 통과"가 아니다.** 한 건만 뒤집히면 미통과다.
발표에서 이 축을 강조하지 않는다.

`DROP`에 대한 유의미한 음성 근거가 하나 나왔다: 수직보호망이 **설치된** 사진
(`H-221025_B21_N-15`)에서 모델이 "방지망 미설치"를 내지 않았다. 대신 그 사진의
진짜 문제(발판 가장자리의 플라스틱 통)를 잡았다. 오탐을 만들지 않았다는 뜻이다.

### 2. `STRUCK` 재시험 → **매핑 한계로 확정**

전도 세트 5장에서 **후보가 단 한 건도 나오지 않았다.** 게이트에서는 5장 중 4장이 0건이었다.
두 번 합쳐 전도 사진 10장에서 `STRUCK` 후보 0건이다.

그런데 `STRUCK` 채택 2건은 또 **다른 세트**에서 나왔다 — 낙하 세트의 사다리차 양중 구역,
선박 블록 조립장 바닥. 둘 다 "바닥에 구획선이 없다"를 정확히 짚었다.

> **결론: 모델 한계가 아니라 데이터 매핑 한계다.**
> 건설 데이터셋에 "부딪힘" 유형이 없어 "전도"로 대체했는데, 전도 사진에는
> `STRUCK`의 탐지 대상(통로·구획선)이 애초에 담겨 있지 않다.

게이트에서 "구분되지 않는다"고 적었던 것이 이제 구분됐다. **미통과 판정은 유지한다** —
축이 되는지 아닌지를 판정할 사진이 없으면 통과시킬 수 없다. 다만 사유를
"모델이 못 본다"가 아니라 **"이 데이터로는 시험할 수 없다"**로 정정한다.

### 3. 축 정의 일관성 — "소화기 부재"·"통로 폐색" → **유지한다**

게이트에서 *"프레임 밖에 있을 수 있어 정지 사진으로 확정 불가"*라고 지적했었다.
`risk-domain.md`가 "유도자 부재"를 제외한 것과 같은 구조라는 문제 제기였다.

평가셋에서 실측 2건이 나왔고, **방향이 반대였다**:

| 사진 | 소화기 실제 | 모델 | 판정 |
|---|---|---|---|
| `H-221020_D11_N-36` 가스용기 대차 | 프레임 안에 없음 | "소화기 부재" 냄 | 맞음 |
| `H-220826_D16_N-34` 용접 작업 | **빨간 소화기가 놓여 있음** | 내지 않음 | 맞음 |

소화기가 있는 사진에서 "부재"라고 하지 않았다. 사람의 부재와 달리 **소화기는 작업
지점 곁에 두는 물건**이라 작업 프레임 안에 들어올 개연성이 높다는 점도 다르다.

→ **유지한다.** 단 이 두 항목이 속한 `FIRE`·`STRUCK`은 어차피 미통과 축이라
**채택률 지표에 들어가지 않는다.** 지표 오염 위험이 없는 상태에서 기능만 남긴다.
두 축이 나중에 통과하게 되면 그때 이 항목을 다시 본다.

## 새로 발견한 실패 모드 — `PPE`의 반려 1건

게이트의 `PPE` 오탐은 "안면보호구를 **내리고 있는데** 보안경 미착용"이었다.
보호구는 보이는데 **착용 상태**를 오독한 것이다.

평가셋의 반려는 성격이 다르다 (`H-220720_D16_N-32`):

> 모델: "작업자가 … **안면에 보안경을 착용하지 않고 맨눈으로** 작업하고 있음"
>
> 실제: 작업자가 고개를 깊이 숙여 **안전모 상면만 보이고 얼굴이 프레임에 없다.**
> 5배 확대해도 눈이 보이지 않는다.

**보이지 않는 것을 단정했다.** 앞의 오탐보다 무거운 유형이다 —
판독 근거가 사진에 존재하지 않는다.

`PPE`는 통과 축이므로 이 실패 모드가 화면에 나갈 수 있다. 완화 수단은 이미 제품에 있다:

1. **채택/반려를 사람이 누른다.** 후보는 기본 "판단 전"이고 자동 반영되지 않는다
2. **근거(`evidence`)를 후보 옆에 항상 띄운다.** 위 건은 근거를 읽는 순간 틀린 게 보인다 —
   "맨눈"이라고 썼는데 사진에 얼굴이 없다
3. **등급은 룰 엔진이 낸다.** 이 후보가 반려돼도 등급 산식은 흔들리지 않는다

프롬프트로 막는 것(예: "얼굴이 보이지 않으면 PPE 판정을 하지 마라")은 **하지 않는다.**
게이트·평가셋 이후에 프롬프트를 고치면 이 두 측정이 무효가 된다.
고칠 거면 세트를 새로 만들고 다시 측정해야 한다. 10/12까지 그럴 시간이 없다.

## 판정자에 대한 고지

게이트와 같다. **`PPE` 정답 라벨 1건을 제외한 15건은 이 저장소를 만든 AI 에이전트가
판정했다.** 독립된 사람의 판단이 아니다.

- 건별 사유를 `eval_adjudication.json`에 남겼다
- 애매한 건은 **반려 쪽으로** 기울였다 (`CAUGHT-1`의 `FALL` 후보).
  채택으로 세면 `FALL`이 4장이 되지만, 확대해도 계단 좌측 단부를 확정할 수 없었다
- 반려 2건 중 1건은 **원본 사진을 5배 확대해** 확인했다 (`FIRE-2`). 확대 이미지는
  스크래치패드에만 두고 저장소에 넣지 않는다

자가채점의 위험은 여전하다. 다만 **두 세트가 독립적으로 같은 결론**을 냈다는 것은
판정자 편향만으로는 설명되지 않는다 — 편향이 있었다면 두 번 다 같은 방향으로
틀렸어야 하는데, 반려율(11% vs 12.5%)과 통과 축 구성이 우연히 맞을 확률은 낮다.

## 이 결과로 바뀌는 것 / 바뀌지 않는 것

| | 상태 |
|---|---|
| `GateStatus` 표 (3축 `PHOTO` / 3축 `CHECKLIST`) | **바뀌지 않음** — 평가셋이 같은 결론 |
| 채택률 지표의 집계 대상 | **바뀌지 않음** — `FALL`·`DROP`·`PPE`만 |
| `STRUCK` 미통과 사유 | **정정** — "구분 안 됨" → "데이터 매핑 한계" |
| "소화기 부재"·"통로 폐색" 유지 여부 | **유지 확정** |
| 발표 시 n 표기 | **추가** — 축별 n을 슬라이드에 명시 (`CAUGHT` 1 / `PPE` 1) |
| 프롬프트·룰 테이블 | **동결** — 측정 후 고치면 측정이 무효가 된다 |
